# Job Orders Routing Operation Expansion Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `JOB_ORDERS` the unified work-order table for both BOM item orders and routing process orders.

**Architecture:** BOM remains the source of item-level production structure: every BOM `SEMI_PRODUCT` child creates an item work order. Each item work order also expands its routing into process work orders in the same `JOB_ORDERS` table, distinguished by `ORDER_KIND = ITEM | OPERATION` and `ROUTING_SEQ`.

**Tech Stack:** NestJS, TypeORM, Oracle, React/Next.js, Jest, pnpm.

---

### Model Rules

- BOM is always the item-structure authority.
- If a BOM child item is `SEMI_PRODUCT`, create an `ITEM` work order for it.
- For every `ITEM` work order, create `OPERATION` work orders from its routing processes.
- `OPERATION` work orders use the same `ITEM_CODE` as the owning `ITEM` work order, and differ by `ROUTING_SEQ` + `PROCESS_CODE`.
- `PARENT_ID` links:
  - BOM child `ITEM` order -> parent `ITEM` order.
  - routing `OPERATION` order -> owning `ITEM` order.
- `ROOT_ORDER_NO` points to the top item work order for all descendants.
- `PROD_RESULTS` should continue accepting `orderNo`; when an operation order is selected, the result naturally belongs to that operation order.
