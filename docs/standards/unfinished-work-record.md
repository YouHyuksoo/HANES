# 미완료 작업 기록 표준

## 목적

작업이 끝까지 마무리되지 않았을 때 다음 세션이나 다른 작업자가 같은 맥락을 다시 추적하지 않도록, 남은 일과 현재 상태를 표준 형식으로 기록한다.

## 기록이 필요한 경우

아래 중 하나라도 해당하면 반드시 미완료 기록을 남긴다.

- 구현, 검증, DB 보정, 배포, 커밋 중 하나라도 완료되지 않았다.
- 테스트나 브라우저 검증이 실패했거나 환경 문제로 실행하지 못했다.
- 사용자의 최종 요청 범위 중 일부만 처리했다.
- 장기 실행 명령, 설치, 서버 실행, 마이그레이션, 데이터 보정이 중간에 끊겼다.
- 다음 작업자가 반드시 알아야 하는 임시 상태, 우회, 위험, 잔여 데이터가 있다.

## 기록 위치

미완료 기록은 아래 위치에 새 파일로 남긴다.

```text
docs/reports/unfinished-work/YYYY-MM-DD-HHMM-<short-slug>.md
```

파일명 규칙:

- 날짜/시간은 KST 기준으로 쓴다.
- `<short-slug>`는 화면, 모듈, 작업 주제를 짧게 쓴다.
- 예: `2026-06-27-2305-aql-iqc-workflow.md`

## 필수 형식

아래 항목은 생략하지 않는다.

```markdown
# 미완료 작업 기록: <작업명>

- 작성시각: YYYY-MM-DD HH:mm KST
- 작성자: <agent/user>
- 작업 범위: <화면/모듈/요청>
- 현재 상태: 진행중 | 차단 | 검증대기 | 사용자결정대기

## 완료한 것

- <완료된 작업과 근거>

## 미완료 / 남은 것

- <남은 작업>

## 변경 파일

- <파일 경로>: <변경 요약>

## 검증 상태

- 실행함: <명령/브라우저/API/DB 확인 결과>
- 실행 못함: <명령과 이유>

## 중단 사유

- <시간 부족, 사용자 중단, 환경 오류, 결정 필요 등>

## 다음 작업자가 바로 할 일

1. <첫 번째 재개 작업>
2. <두 번째 재개 작업>

## 주의사항

- <되돌리면 안 되는 변경, 잔여 데이터, 서버/포트 상태, 사용한 계정 등>
```

## 재개 절차

작업을 시작할 때 아래 순서로 확인한다.

1. `docs/reports/unfinished-work/`에 현재 요청과 관련된 기록이 있는지 확인한다.
2. 관련 기록이 있으면 `완료한 것`, `미완료 / 남은 것`, `검증 상태`, `주의사항`을 먼저 읽는다.
3. 코드와 DB는 기록을 그대로 믿지 않고 현재 상태를 다시 확인한다.
4. 작업을 이어서 완료하면 해당 기록에 결과를 덮어쓰지 않는다. 새 최종 응답에서 완료 사실과 검증 결과를 명시한다.
5. 기록 내용이 더 이상 위험하지 않더라도 삭제하지 않는다. 과거 중단 이력으로 보존한다.

## 금지

- "나중에 이어서 하면 됨"처럼 대화에만 남기고 파일 기록을 생략하지 않는다.
- 실패한 명령을 숨기지 않는다.
- 검증하지 않은 상태를 PASS로 쓰지 않는다.
- 사용자 변경이나 다른 AI 변경을 임의로 되돌리지 않는다.
