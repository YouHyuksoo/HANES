# 워크플로우 중심형 지식맵 설계

- 작성일: 2026-09-02
- 상태: 설계 승인됨 (구현 대기)

## 1. 배경과 문제

현재 `/workflow`는 `가이드`, `흐름도`, `전체구성도` 세 가지 관점을 제공한다. 기존 화면은 정해진 업무 순서와 전체 업무 레인을 이해하는 데 유용하지만, 사용자가 궁금한 업무·화면·기준정보·테이블·예외를 중심에 놓고 관련 조건과 처리 근거를 단계적으로 탐색하기는 어렵다.

새 지식맵은 사용자가 `입하 등록`, `MAT_LOTS`, `IQC 불합격`, `출하 전에 꼭 해야 하는 것`처럼 대상을 찾으면 해당 대상을 중심으로 검수된 관계를 펼쳐 보여준다. AI는 질문을 중심 후보와 관계 필터로 해석할 뿐, 관계를 임의 생성하지 않는다.

## 2. 목표 / 비목표

### 목표

- 기존 세 탭을 보존하고 네 번째 `지식맵` 탭을 추가한다.
- 업무, 화면, 기준정보, 제약조건, 필수작업, 예외상황, 처리로직, 데이터, 기술근거를 하나의 공유 그래프로 표현한다.
- 기본 1홉만 표시하고 사용자가 노드를 클릭해 관계를 점진 확장한다.
- `마인드맵`, `프로세스`, `관계도` 레이아웃을 사용자가 전환한다.
- `업무 보기`, `기술 보기`가 같은 그래프를 서로 다른 관점으로 강조한다.
- 정확 검색과 AI 보조 해석을 함께 제공하되, 화면에는 공유 그래프에 등록된 관계만 표시한다.
- 현재 `workflowMap`의 모든 업무 노드를 검색 가능한 초기 골격으로 전환한다.
- 관계의 근거와 문서화 품질을 사용자에게 명시한다.
- 중심과 보기 상태를 URL로 공유하고 탐색 이력을 제공한다.

### 비목표

- 첫 버전에서 화면상 그래프 편집 기능을 제공하지 않는다.
- AI가 새 업무 규칙이나 관계를 생성하도록 하지 않는다.
- 기존 `가이드`, `흐름도`, `전체구성도`를 교체하거나 동작을 변경하지 않는다.
- 첫 버전에서 이미지/PDF 내보내기와 개인 메모를 구현하지 않는다.
- 모바일/PDA에서 PC와 동일한 캔버스 편집·탐색 밀도를 제공하지 않는다.

## 3. 설계 결정 요약

| 결정 | 선택 | 근거 |
|---|---|---|
| 중심 대상 | 업무·화면·테이블·조건·예외를 포함한 통합 탐색 | 사용자가 알고 싶은 개념에서 탐색을 시작할 수 있다. |
| 확장 깊이 | 기본 1홉, 클릭 확장 | 전체 맥락과 가독성을 함께 유지한다. |
| 데이터 원천 | 검수된 공유 지식 그래프 | 프론트와 백엔드가 같은 의미 모델을 사용하고 AI 추측을 차단한다. |
| 레이아웃 | 마인드맵 기본, 프로세스·관계도 선택 | 기존 흐름도와 역할을 구분하면서 사용자 목적에 맞게 전환한다. |
| 노드 클릭 | 확장과 상세 표시, 중심 이동은 별도 버튼 | 사용자가 현재 맥락을 잃지 않는다. |
| 보기 모드 | 업무/기술 보기 | 운영자와 개발자가 같은 그래프를 다른 밀도로 활용한다. |
| 검색 | 정확 검색 우선, AI 보조 해석 | 속도와 일관성을 유지하면서 자연어 진입을 지원한다. |
| 편집 | 조회 전용 | 권한·이력·충돌 문제를 첫 범위에서 제외한다. |
| 공유 | URL 상태 공유 | 같은 분석 관점을 재현할 수 있다. |
| 시각 방향 | 산업 설계도형 `Knowledge Blueprint` | 복잡한 MES 관계를 전문 분석 도구처럼 명료하게 표현한다. |

## 4. 상세 설계

### 4.1 공유 지식 그래프

업무 의미 모델은 React 컴포넌트나 화면 좌표를 포함하지 않는 공유 패키지에 둔다. 프론트는 이를 렌더링하고 백엔드는 검색 및 AI 해석 결과 검증에 사용한다.

노드 종류:

- `activity`: 입하 등록, IQC 검사, 출하 확정 같은 업무
- `screen`: 업무를 수행하거나 조회하는 화면
- `master`: 품목, 거래처, 창고, AQL 정책 같은 기준정보
- `constraint`: 재고, 상태, 설정값 등에 관한 제약조건
- `requiredTask`: 중심 업무 전에 반드시 완료할 작업
- `exception`: 불합격, 중복, 부족, 상태 불일치 같은 예외상황
- `logic`: 특채, 재검사, 취소, 복구 같은 처리로직
- `data`: 테이블 또는 주요 데이터 객체
- `evidence`: API, Service, 도움말, 업무 문서, 소스 위치

관계 종류:

- `precedes`, `follows`, `requires`, `references`, `validates`
- `branchesTo`, `raises`, `recoversWith`
- `reads`, `writes`, `evidencedBy`

각 노드는 고유 ID, 제목, 요약, 검색 별칭, 보기 모드, 문서화 상태를 가진다. 각 관계는 시작·종료 노드, 종류, 방향, 짧은 관계 문장, 선택적 조건식, 근거 ID를 가진다.

문서화 상태는 다음 세 값으로 제한한다.

- `verified`: 현재 코드·문서·DB 구조에서 근거가 확인됨
- `partial`: 연결은 확인했지만 세부 조건 근거가 부족함
- `undocumented`: 기존 업무는 있으나 요청 관계 정보가 아직 없음

`없음`은 검토 결과 해당 관계가 존재하지 않는 상태이고, `미문서화`는 아직 판단할 근거가 부족한 상태이므로 UI에서 구분한다.

### 4.2 기존 데이터 수용

초기 변환기는 `workflowMap.ts`의 모든 `WorkflowActivityNode`를 `activity` 노드로 가져온다.

- `routes`는 `screen` 노드와 `references` 관계로 변환한다.
- `dataObjects`는 `data` 노드와 `reads` 또는 `writes` 후보 관계로 변환한다. 읽기/쓰기 방향이 근거로 확인되지 않으면 단순 `references`로 유지한다.
- `inputs`, `outputs`, `why`, `when`, `cautions`는 상세 설명과 검색 인덱스에 사용한다.
- `workflowEdges`는 업무 간 `precedes`, `branchesTo`, `recoversWith`, `references`로 매핑한다.
- 조건·예외·처리로직은 코드, 도움말, `docs/workflows/definitions`, `docs/business-logics`에서 확인된 항목만 추가한다.

기존 `workflowMap.ts`를 한 번에 제거하지 않는다. 초기에는 어댑터로 공유 그래프와 연결하고, 중복 데이터 제거는 별도 후속 결정으로 남긴다.

### 4.3 페이지와 컴포넌트 경계

`page.tsx`는 탭 상태와 기존 탭 간 선택 연결만 담당한다. 지식맵은 별도 기능 경계로 구성한다.

| 단위 | 책임 |
|---|---|
| `WorkflowKnowledgeMap` | 화면 조립과 탐색 상태 관리 |
| `KnowledgeSearch` | 정확·별칭 검색과 AI 후보 표시 |
| `KnowledgeToolbar` | 레이아웃, 보기 모드, 이력, 공유 제어 |
| `RelationFilters` | 관계 범주별 표시와 숨김 |
| `KnowledgeCanvas` | React Flow 캔버스와 렌더링 |
| `KnowledgeNode` | 노드 종류별 형태, 아이콘, 품질 상태 표시 |
| `KnowledgeEdge` | 관계 종류별 선, 방향, 조건 라벨 표시 |
| `KnowledgeDetailPanel` | 설명, 조건, 근거, 바로가기 표시 |
| `useKnowledgeNavigation` | 중심 이동과 뒤로·앞으로 이력 |
| `knowledge-graph` | 검색, 1홉 추출, 확장, 필터링 |
| `knowledge-layouts` | 세 레이아웃의 좌표 계산 |

### 4.4 탐색 상태와 동작

1. 사용자가 검색 결과 또는 기존 업무 노드에서 중심을 선택한다.
2. 중심과 활성 관계 범주의 1홉 이웃을 표시한다.
3. 주변 노드 클릭은 상세패널을 열고 해당 노드의 다음 관계를 펼친다.
4. `중심으로 보기`를 누르면 중심이 이동하고 이전 중심은 탐색 이력에 남는다.
5. 레이아웃과 보기 모드를 전환해도 선택·확장 상태는 유지한다.
6. 빈 공간 클릭은 선택만 해제하고 확장 상태는 보존한다.
7. 전체 펼치기는 예상 노드 수가 임계값을 넘으면 모달로 확인한다.

URL에는 다음 재현 가능한 상태만 기록한다.

- 중심 노드 ID
- 레이아웃
- 업무/기술 보기 모드
- 활성 관계 필터

임시 확장 노드와 패널 스크롤 같은 세부 UI 상태는 URL에 넣지 않는다. 마지막 레이아웃과 보기 모드는 로컬 저장소에 보존하되 URL 값이 있으면 URL을 우선한다.

### 4.5 레이아웃

- `mindmap`: 중심에서 관계 범주별 가지가 방사형으로 펼쳐진다. 기본 레이아웃이다.
- `process`: 선행과 필수작업은 왼쪽, 중심은 중앙, 후행과 결과는 오른쪽, 예외와 복구는 하단에 둔다.
- `relation`: 업무 흐름은 수평 축, 기준정보·제약·테이블·근거는 상하 보조 축에 둔다.

레이아웃 함수는 그래프 의미와 좌표 계산을 분리하며 동일한 노드 집합을 입력받는다. 계산 실패 시 겹침을 최소화한 단순 방사형 배치로 복구한다.

현재 중심과 사용자가 펼친 노드만 React Flow에 전달한다. 전체 검색 인덱스는 공유 그래프 전체에서 미리 생성하되, 전체 노드를 DOM에 렌더링하지 않는다.

### 4.6 검색과 AI 보조 해석

정확 검색은 제목, ID, 메뉴 경로, 테이블명, 별칭을 대상으로 클라이언트에서 즉시 수행한다. 자연어 질문은 백엔드가 다음 제한된 결과만 반환한다.

- 공유 그래프에 존재하는 중심 후보 ID
- 허용된 관계 종류 목록
- 사용자의 선택을 돕는 짧은 해석 문장

프론트와 백엔드는 응답의 노드 및 관계 종류를 공유 스키마로 다시 검증한다. 미등록 값은 버리고 정확 검색 결과를 유지한다. AI 응답만으로 중심을 즉시 변경하지 않고 사용자가 후보를 선택해야 적용한다.

### 4.7 상세패널

상세패널은 노드 종류에 맞춰 다음 정보를 우선순위로 표시한다.

- 업무 보기: 목적, 수행 시점, 선행작업, 조건, 예외, 처리 결과
- 기술 보기: 화면 경로, API, Service, 테이블, 주요 컬럼, 근거 파일
- 공통: 문서화 상태, 들어오는 관계, 나가는 관계, `중심으로 보기`, 관련 화면 바로가기

파일 근거는 repo 상대경로와 식별자를 표시한다. 화면 경로는 앱 내부 링크로 이동한다. 기술 근거가 없는 경우 빈 영역을 숨기지 않고 `미문서화`로 표시한다.

### 4.8 시각 디자인과 반응형

밝은 도면 배경, 미세 그리드, 청회색 업무 노드와 안전표지 계열 강조색을 사용한다. 중심 노드는 정밀 카드 또는 육각형 실루엣으로 강조하고, 조건은 황색 다이아몬드, 예외는 적색 경고, 기준정보는 청록색, 데이터는 모노스페이스 청색으로 구분한다.

색상만으로 의미를 전달하지 않는다. 노드 형태, 아이콘, 선 패턴, 관계 라벨을 함께 사용한다. 가지 확장 시 짧은 순차 등장 애니메이션을 적용하고 `prefers-reduced-motion`에서는 제거한다.

- 1440px 이상: 좌측 관계 필터, 중앙 캔버스, 우측 상세패널 동시 표시
- 작은 노트북: 상세패널을 우측 오버레이로 전환
- 모바일/PDA: 검색, 중심 이동, 상세 조회 중심의 간소화 레이아웃

키보드로 검색 결과, 도구막대, 노드, 상세패널에 접근할 수 있어야 한다. 현재 중심과 선택 상태는 시각 표현 외에 접근성 속성으로도 전달한다.

## 5. 에러 처리

- AI 검색 실패 시 정확 검색과 그래프 탐색은 계속 동작한다.
- URL의 중심 ID가 유효하지 않으면 오류 안내와 검색 후보를 표시하고 임의 중심으로 조용히 대체하지 않는다.
- 잘못된 관계는 해당 관계만 제외하고 유효한 서브그래프는 렌더링한다.
- 레이아웃 계산 실패 시 단순 방사형 배치로 복구한다.
- 관계가 없을 때 `없음`과 `미문서화`를 구분한다.
- 전체 펼치기로 노드 수가 임계값을 넘으면 예상 수를 표시한 확인 모달을 사용한다.
- 네이티브 `alert`, `confirm`, `prompt`는 사용하지 않는다.

## 6. 테스트 전략

### 자동 테스트

- 노드·관계 ID 고유성과 참조 무결성
- 화면 경로 및 근거 참조 형식
- 명시되지 않은 순환 관계와 고아 노드 검출
- 기존 `workflowMap` 전체 업무의 검색 인덱스 포함
- 1홉 추출, 점진 확장, 중복 제거
- 관계 필터별 포함·제외
- 세 레이아웃 전환 시 선택·확장 상태 유지
- 중심 이동 뒤로·앞으로 이력
- URL 직렬화와 복원
- AI 응답의 미등록 노드·관계 거부
- 반응형 상세패널과 키보드 접근성
- frontend/backend focused typecheck

### 브라우저 시나리오

1. `입하 등록`을 검색해 마인드맵 중심으로 이동한다.
2. 기준정보, 필수작업, 관계테이블만 필터링한다.
3. `IQC 불합격` 질문에서 후보를 선택하고 예외와 처리로직을 확인한다.
4. 예외 노드를 확장해 근거와 관련 화면을 연다.
5. 세 레이아웃을 전환해 선택과 확장 상태 유지를 확인한다.
6. 중심 이동 후 뒤로·앞으로를 확인한다.
7. 공유 URL을 새 탭에서 열어 중심, 보기, 필터 복원을 확인한다.
8. AI API 실패 상태에서 정확 검색과 탐색이 유지되는지 확인한다.

### 완료 기준

- 기존 세 탭의 회귀 없이 `지식맵` 탭이 추가된다.
- 현재 등록된 모든 업무 노드가 검색 가능하다.
- 검증된 1홉 관계가 모든 중심에서 안정적으로 표시된다.
- `없음`, `부분 확인`, `미문서화`가 구분된다.
- 업무 사용자와 개발자가 같은 그래프를 각 보기 모드로 이해할 수 있다.
- 근거 없는 AI 생성 관계는 표시되지 않는다.
- 1440px PC와 작은 노트북에서 핵심 기능을 사용할 수 있다.

## 7. 제외한 대안

### 프론트엔드 전용 확장

현재 1,163줄인 `workflowMap.ts`에 모든 의미 관계와 UI 표현을 함께 추가하면 구현은 빠르지만 파일 책임이 더 커지고 백엔드 검색에서 재사용하기 어렵다.

### 문서/RAG 중심 동적 그래프

현재 워크플로우 문서는 전체 화면, 테이블, 조건, 예외를 모두 담지 않는다. 재색인 상태에 따라 핵심 UI 결과가 달라질 수 있으므로 검수된 공유 그래프를 확정 원천으로 사용하고 문서/RAG는 근거와 검색 보조로 제한한다.

### AI 실시간 그래프 생성

같은 질문에도 결과가 달라지고 누락 또는 허위 관계를 사용자가 구분하기 어렵다. AI는 질문 해석만 수행하고 관계 생성 권한을 갖지 않는다.

### 기존 전체구성도 교체

고정된 전체 시스템 시야와 중심 기반 탐색은 목적이 다르다. 초기에는 네 번째 탭으로 분리하고 실제 사용 결과를 확인한 뒤 정보 구조 통합 여부를 판단한다.
